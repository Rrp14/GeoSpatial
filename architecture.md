# Geospatial File Measurement API --- System Architecture

**Status:** Locked design\
**Primary goal:** Build a production-minded geospatial file-processing
API that securely accepts Shapefile/KML uploads, scans and isolates
untrusted files, extracts features, calculates defensible spatial
measurements, persists metadata/results, and exposes a minimal React
interface.

------------------------------------------------------------------------

## 1. Design Goals

The system must:

-   Accept `.kml` files and `.zip` archives containing a Shapefile.
-   Treat every uploaded file as untrusted.
-   Store uploads in object storage rather than the API container
    filesystem.
-   Quarantine every new upload until malware scanning succeeds.
-   Validate archive structure and geospatial content before processing.
-   Extract feature ID/index, geometry type, geometry, CRS, and
    properties.
-   Calculate area for Polygon/MultiPolygon and length for
    LineString/MultiLineString.
-   Gracefully handle Point/MultiPoint and unsupported geometries.
-   Never calculate physical measurements directly from
    latitude/longitude degree values.
-   Persist file metadata, processing state, features, measurements,
    warnings, and errors.
-   Be runnable as a reproducible Docker Compose stack.
-   Keep processing logic independent from HTTP so it can later move to
    a background worker.
-   Provide a minimal modern React UI for uploading and viewing
    files/results.

### Non-goals for V1

The first version will not include:

-   User authentication/authorization.
-   Interactive GIS maps.
-   Spatial database queries requiring PostGIS.
-   Kubernetes.
-   Kafka.
-   WebSockets.
-   A distributed worker queue.
-   Automatic modification/repair of invalid geometries without
    reporting it.
-   Arbitrary CRS guessing when CRS metadata is missing.

These can be added only when requirements justify them.

## 4. Docker Topology

All application dependencies are shipped as containers.

``` text
docker-compose.yml
|
+-- frontend        React/Vite UI
+-- api             FastAPI application
+-- postgres        PostgreSQL database
+-- minio           S3-compatible object storage
+-- clamav          clamd + malware signatures
```

A future production evolution may add:

``` text
+-- worker          asynchronous geospatial processing
+-- redis           queue/broker
```

The processing domain code must be designed now so adding a worker later
does not require rewriting geospatial logic.

### Network policy

Conceptually:

``` text
Public/host access
|
+-- frontend
+-- api
+-- MinIO console (development only)

Internal Docker network
|
+-- api <-> postgres
+-- api <-> minio
+-- api <-> clamav
```

ClamAV port `3310` should be exposed only to the Docker network, not
published publicly. PostgreSQL should similarly avoid public exposure in
production.

### Persistent volumes

``` text
postgres_data  -> PostgreSQL data
minio_data     -> uploaded objects
clamav_db      -> ClamAV signature database
```

Containers are disposable; persistent state is not.

### Why this structure?

The main rule is dependency direction:

``` text
HTTP/API
   |
   v
Services / use cases
   |
   +------> repositories ------> database
   |
   +------> geo domain --------> GeoPandas/PyProj/Shapely
   |
   +------> storage ----------- > MinIO
   |
   +------> scanner -----------> ClamAV
```

Routes should not contain hundreds of lines of ZIP, GeoPandas,
SQLAlchemy, MinIO, and ClamAV code.

The HTTP layer coordinates requests and responses. Domain/service layers
perform actual work.

## 6. File Lifecycle / State Machine

Every file begins untrusted.

``` text
UPLOADING
    |
    v
QUARANTINED
    |
    v
SCANNING
    |
    +------------------+
    |                  |
    v                  v
CLEAN              INFECTED
    |                  |
    v                  v
VALIDATING          REJECTED
    |
    v
PROCESSING
    |
    +---------------------+
    |                     |
    v                     v
COMPLETED         PROCESSING_FAILED
```

Additional failure states can be represented using an error code while

Example error codes:

``` text

ARCHIVE_TOO_LARGE
SHAPEFILE_COMPONENT_MISSING
MALWARE_DETECTED
CRS_MISSING
CRS_INVALID
GEOMETRY_INVALID
PROCESSING_ERROR
STORAGE_ERROR
SCAN_ERROR
```

## 7. End-to-End Upload Workflow

### Step 1 --- Client selects a file

The React UI accepts:

``` text
.kml
.zip
```

Client-side validation is only convenience. It is never trusted as
security validation.

### Step 2 --- Upload request

``` http
POST /api/files/
Content-Type: multipart/form-data
```

FastAPI receives the upload using `UploadFile`.

The API performs cheap checks first:

-   extension allowlist;
-   configured maximum upload size;
-   non-empty filename/file;
-   supported media category where useful;
-   generated server-side UUID.

The original filename is metadata only and is never used as the physical
storage path.

### Step 3 --- Database record created

Example:

``` text
id: UUID
original_filename: survey.zip
file_type: SHAPEFILE_ZIP
status: UPLOADING
```

### Step 4 --- Store in MinIO quarantine bucket

Object key:

``` text
geo-quarantine/{file_uuid}/original.zip
```

The status becomes:

``` text
QUARANTINED
```

No geospatial parser touches the file at this point.

### Step 5 --- Malware scan

The API/storage layer streams the object from MinIO to ClamAV using
`clamd`'s streaming scan protocol.

ClamAV does not receive MinIO credentials.

``` text
MinIO -> API/scanner client -> clamd
```

Status:

``` text
SCANNING
```

#### Clean

Continue.

#### Infected

Set:

``` text
status = REJECTED
error_code = MALWARE_DETECTED
```

The object remains isolated in quarantine or is deleted according to
retention policy.

It is never copied into the clean bucket and never parsed.

#### Scanner unavailable

Do **not** fail open.

The upload stays quarantined and processing stops with a scan/service
error.

### Step 6 --- Promote clean object

After a successful scan:

``` text
geo-quarantine/{uuid}/original.zip
            |
            v
geo-clean/{uuid}/original.zip
```

After successful promotion, the quarantine copy can be removed according
to policy.

### Step 7 --- Structural validation

For KML:

-   file can be opened;
-   driver recognizes it;
-   content is valid enough for parsing.

For Shapefile ZIP:

-   safe archive paths only;
-   no path traversal;
-   no unexpected symlink behavior;
-   archive member count below limit;
-   compressed size below limit;
-   total uncompressed size below limit;
-   required logical Shapefile components exist.

Required:

``` text
.shp
.shx
.dbf
```

Normally expected for CRS-aware measurement:

``` text
.prj
```

Optional:

``` text
.cpg
```

Multiple unrelated Shapefile datasets inside one archive should be
rejected in V1 rather than ambiguously choosing one.

### Step 8 --- Read geospatial dataset

The format-specific reader produces a common internal representation:

``` text
KML -----------+
               |
               v
          GeoDataFrame
               ^
               |
Shapefile -----+
```

Everything downstream should operate on this normalized representation
rather than contain KML/Shapefile-specific branches.

### Step 9 --- Validate CRS

The system determines:

-   source CRS;
-   whether it is geographic or projected;
-   units;
-   whether the CRS is suitable for direct physical measurement.

Missing CRS is not silently interpreted as EPSG:4326.

Instead:

``` text
CRS_MISSING
```

A future API option may allow the caller to explicitly supply a source
CRS override.

### Step 10 --- Validate geometries

For every geometry:

1.  Is it null?
2.  Is it empty?
3.  What geometry type is it?
4.  Is it valid?
5.  Is its type supported?
6.  Can it safely be measured?

Invalid/unsupported individual features should normally generate
feature-level status/warnings instead of crashing the entire file.

### Step 11 --- Select measurement strategy

See the CRS/measurement section below.

### Step 12 --- Calculate measurements

Supported behavior:

  Geometry             Result
  -------------------- -------------------
  Point                no measurement
  MultiPoint           no measurement
  LineString           length
  MultiLineString      total length
  Polygon              area
  MultiPolygon         total area
  GeometryCollection   unsupported in V1
  Unknown              unsupported

Canonical storage units:

``` text
length -> metres
area   -> square metres
```

Conversion to km/km²/hectares can happen at the response/presentation
layer later.

### Step 13 --- Persist results

Persist:

-   file metadata;
-   source CRS;
-   measurement strategy metadata;
-   feature count;
-   geometry;
-   feature properties;
-   measurement values;
-   units;
-   warnings;
-   unsupported feature statuses;
-   processing timestamps.

### Step 14 --- Complete

``` text
status = COMPLETED
```

The UI refreshes file details and measurements.

## 8. CRS and Measurement Design

### Core rule

Never use planar Shapely `.area` or `.length` directly on
latitude/longitude degrees and present the result as physical
area/distance.

### Why not always UTM?

UTM is excellent for relatively local datasets, but one selected UTM
zone becomes questionable for:

-   datasets crossing multiple UTM zones;
-   very wide features;
-   continental data;
-   global data;
-   unusual high-latitude cases.

Therefore UTM is a strategy, not a universal rule.

### Strategy interface

``` text
MeasurementStrategy
|
+-- ProjectedMeasurementStrategy
|
+-- GeodesicMeasurementStrategy
```

A `MeasurementStrategySelector` chooses the method based on CRS,
geometry type, and extent.

### Projected strategy

Suitable for local/regional data.

``` text
source geographic CRS
        |
        v
select suitable projected CRS
        |
        v
transform geometry
        |
        v
Shapely planar measurement
```

Possible projected choices:

-   local UTM for compact local datasets;
-   an appropriate equal-area projection when area preservation is more
    important and the extent makes UTM undesirable.

### Geodesic strategy

For geographic data whose extent makes a single local projection
inappropriate:

``` text
geometry
   |
   v
normalize geographic coordinates
   |
   v
PyProj Geod / ellipsoid
   |
   +--> geodesic length in metres
   |
   +--> geodesic area in square metres
```

### Selection concept

``` text
                       source CRS
                           |
                 +---------+---------+
                 |                   |
             projected            geographic
                 |                   |
                 v                   v
          usable metric?        inspect extent
             /      \              /      \
           yes      no          local      wide
            |        |            |          |
            v        v            v          v
         planar   transform      UTM/     geodesic
         measure  or geodesic  suitable
                              projection
```

### Why retain both?

The assignment explicitly expects projected-CRS handling. A projected
strategy demonstrates that requirement directly.

The geodesic strategy gives the system a defensible solution for
datasets where forcing everything into one UTM zone would be weaker
engineering.

Every measurement response should expose the method used.

Example:

``` json
{
  "type": "AREA",
  "value": 154232.71,
  "unit": "m2",
  "method": "PROJECTED",
  "source_crs": "EPSG:4326",
  "measurement_crs": "EPSG:32643"
}
```

or:

``` json
{
  "type": "LENGTH",
  "value": 912340.22,
  "unit": "m",
  "method": "GEODESIC",
  "source_crs": "EPSG:4326",
  "measurement_crs": null,
  "ellipsoid": "WGS84"
}
```

### `uploaded_files`

``` text
processed_at           TIMESTAMP NULL
```

### `features`

``` text
id                UUID PK
file_id           UUID FK -> uploaded_files.id
feature_index     INTEGER
source_feature_id VARCHAR NULL
geometry_type     VARCHAR
geometry_json     JSONB
properties        JSONB
status            VARCHAR
warning           TEXT NULL
```

### `measurements`

``` text
id                  UUID PK
feature_id           UUID FK -> features.id
measurement_type     VARCHAR
value                DOUBLE PRECISION NULL
unit                 VARCHAR NULL
method               VARCHAR NULL
measurement_crs      VARCHAR NULL
ellipsoid            VARCHAR NULL
status               VARCHAR

```

### Optional `processing_events`

Useful for debugging/auditing without bloating the main file table.

``` text
id          UUID PK
file_id     UUID FK
stage       VARCHAR
level       VARCHAR
message     TEXT
created_at  TIMESTAMP
```

### Why PostgreSQL rather than SQLite?

**Pros**

-   proper concurrent database;
-   strong JSONB support for arbitrary feature attributes;
-   realistic production deployment;
-   clean future path to PostGIS;
-   reliable transactions.

**Cons**

-   another service to operate;
-   heavier local setup than SQLite.

Because Docker Compose already manages infrastructure and the project is
explicitly production-minded, PostgreSQL is justified.

### Why not PostGIS now?

**PostGIS advantages**

-   native spatial columns/indexes;
-   spatial SQL;
-   intersections, proximity, containment;
-   efficient spatial queries.

**Why defer it**

The current requirements are file processing and measurement, not
spatial querying. GeoPandas/Shapely/PyProj already perform the required
geometry work.

Adding PostGIS immediately creates schema and deployment complexity
without solving a current problem.

**Future trigger:** add PostGIS when the API needs spatial search/query
operations.

## 10. Object Storage Design

### Buckets

``` text
geo-quarantine
geo-clean
```

Possible future:

``` text
geo-results
```

### Why MinIO?

**Pros**

-   S3-compatible API;
-   works locally in Docker;
-   avoids tying processing to API-container disk;
-   clean future migration to S3-compatible cloud storage;
-   object lifecycle is explicit;
-   good fit for potentially large uploads.

**Cons**

-   additional service;
-   credentials and bucket policies must be managed;
-   more operational work than local filesystem storage.

### Alternative: local filesystem

**Pros**

-   simplest implementation;
-   no additional service.

**Cons**

-   container-local files are ephemeral unless volumes are managed;
-   awkward horizontal scaling;
-   harder security/storage separation;
-   weaker production architecture.

MinIO is selected because file storage is a first-class concern in this
project.

## 11. Malware Scanning Design

### Selected: ClamAV `clamd`

Every file is quarantined before scanning.

### Why ClamAV?

**Pros**

-   open source;
-   established malware scanning engine;
-   Docker-friendly;
-   daemon supports streamed scanning;
-   signature updates available through FreshClam;
-   keeps the security boundary visible in the architecture.

**Cons**

-   memory-heavy;
-   signature-based scanning cannot guarantee that a file is safe;
-   startup/signature loading can take time;
-   scanner availability becomes part of the upload pipeline.

### Alternative: cloud malware scanning service

**Pros**

-   managed infrastructure;
-   may provide multiple detection engines.

**Cons**

-   cost;
-   privacy/data-transfer concerns;
-   external dependency;
-   harder offline/local evaluation;
-   potentially unsuitable for confidential geospatial uploads.

### Alternative: no malware scan

Simpler, but unacceptable for the architecture we are intentionally
building because the application passes untrusted archives/files into
complex native geospatial parsers.

### Fail-closed rule

If ClamAV is unavailable:

``` text
do not process the file
```

The object stays quarantined.

## 12. Archive Security

ZIP processing is not merely `extractall()`.

The validator must enforce:

-   allowed file extension;
-   maximum upload size;
-   maximum member count;
-   maximum total expanded size;
-   maximum compression ratio where practical;
-   safe normalized paths;
-   no `../` traversal;
-   no extraction outside a generated temporary directory;
-   reject ambiguous multiple Shapefile datasets;
-   required Shapefile components;
-   cleanup temporary extraction directories.

Archive extraction occurs only after malware scanning.

## 14. Error Response Contract

Errors should be predictable.

``` json
{
  "error": {
    "code": "CRS_MISSING",
    "message": "The uploaded dataset does not define a coordinate reference system.",
    "details": null
  }
}
```

Do not leak:

-   stack traces;
-   filesystem paths;
-   MinIO secrets;
-   database connection information;
-   internal ClamAV details not useful to the client.

Detailed exceptions belong in structured server logs.

framework-level routing infrastructure for this two-page API client.

## 16. Backend Framework Decision

### Selected: FastAPI

**Pros**

-   natural fit for API-first services;
-   excellent request/response schema integration;
-   automatic OpenAPI documentation;
-   async-capable;
-   `UploadFile` fits streaming upload workflows;
-   lower framework overhead for this use case.

**Cons**

-   fewer batteries included than Django;
-   architecture discipline must be imposed by us;
-   background/distributed jobs require additional infrastructure when
    needed.

### Alternative: Django + Django REST Framework

**Pros**

-   mature ORM/admin/auth ecosystem;
-   strong conventions;
-   excellent for larger database-heavy business applications.

**Cons**

-   more framework machinery than this processing service requires;
-   Django admin/auth/template features are not core requirements.

FastAPI is selected because this system is primarily an API and
processing pipeline.

------------------------------------------------------------------------

## 17. Geospatial I/O Decision

### Selected: GeoPandas + Pyogrio/GDAL

**Pros**

-   common Python geospatial abstraction;
-   Shapefile/KML support through GDAL ecosystem;
-   normalized GeoDataFrame representation;
-   integrates naturally with Shapely and PyProj.

**Cons**

-   native geospatial dependencies make Docker images larger;
-   GDAL errors can be less friendly than pure Python libraries;
-   large datasets require memory awareness.

### Alternative: manually parse formats

Rejected. Shapefile and KML have mature geospatial tooling; hand-writing
parsers would add risk without demonstrating useful engineering.

------------------------------------------------------------------------

## 18. Geometry Library Decision

### Selected: Shapely

Use for:

-   geometry type handling;
-   validity checks;
-   planar measurement after projection;
-   geometry serialization/conversion operations.

**Pros**

-   standard Python geometry library;
-   integrates with GeoPandas;
-   robust GEOS-backed operations.

**Cons**

-   planar calculations are only meaningful when CRS/units are
    appropriate;
-   native dependency through GEOS.

The CRS layer must therefore guard measurement use.

------------------------------------------------------------------------

## 19. Processing Model Decision

### V1: synchronous orchestration

Initial flow:

``` text
request
 -> quarantine
 -> scan
 -> validate
 -> process
 -> persist
 -> response
```

### Why start synchronously?

**Pros**

-   easier to implement and test;
-   fewer infrastructure dependencies;
-   sufficient for an assignment-sized workload;
-   lets us focus on correctness.

**Cons**

-   long-running uploads hold requests open;
-   poor fit for very large files;
-   API worker capacity can be consumed by CPU-heavy processing.

### Future: queue + worker

``` text
FastAPI
   |
   v
store + enqueue
   |
   v
Redis/RabbitMQ
   |
   v
Worker
   |
   v
same ProcessingService
```

The crucial architectural rule is that `ProcessingService` cannot depend
on FastAPI request objects. That makes migration to workers
straightforward.

## 22. Testing Strategy

### Unit tests

Test pure behavior aggressively:

-   extension validation;
-   archive path traversal rejection;
-   archive size/member limits;
-   Shapefile component validation;
-   geometry type classification;
-   missing CRS handling;
-   CRS strategy selection;
-   projected area;
-   projected length;
-   geodesic length;
-   geodesic area;
-   unsupported geometry handling.

### Integration tests

Run against real service dependencies where appropriate:

``` text
FastAPI + PostgreSQL + MinIO + ClamAV
```

Important scenarios:

1.  valid KML;
2.  valid Shapefile ZIP;
3.  missing `.shx`;
4.  missing CRS;
5.  malicious/invalid archive path;
6.  oversized archive;
7.  unsupported extension;
8.  invalid geometry;
9.  mixed supported/unsupported features;
10. ClamAV unavailable;
11. infected test file using a safe antivirus test signature;
12. MinIO failure;
13. database failure/rollback behavior.

### Why fixture files?

Geospatial processing should be tested with known small datasets whose
expected measurements are known within explicit tolerances.

Do not assert floating-point geographic measurements using exact
equality.

## 23. Security Boundaries

``` text
UNTRUSTED
Client upload
    |
    v
FastAPI validation
    |
    v
MinIO quarantine
    |
    v
ClamAV
    |
---- TRUST GATE ---------------------------------
    |
    v
archive extraction
    |
    v
GDAL/Pyogrio
    |
    v
measurement processing
```

Malware scanning reduces risk but does not make input inherently
trustworthy. Structural validation and safe extraction remain mandatory.

Additional controls:

-   generated storage keys;
-   no execution permission for uploads;
-   no user-controlled filesystem paths;
-   bounded uploads;
-   bounded decompression;
-   bounded feature/result pagination;
-   no public quarantine bucket;
-   least-privilege MinIO credentials;
-   no public clamd port;
-   sanitized API errors.

## 27. Architecture Rule to Preserve

The most important maintainability rule for the implementation is:

``` text
FastAPI is an adapter, not the application.
MinIO is an adapter, not the application.
ClamAV is an adapter, not the application.
PostgreSQL is an adapter, not the application.
GeoPandas is a tool used by the geospatial domain.

The processing workflow belongs in services/domain modules.
```

If we preserve that boundary, the system can later replace MinIO with
S3, synchronous execution with workers, PostgreSQL with
PostgreSQL+PostGIS, or React with another client without rewriting the
core measurement logic.
